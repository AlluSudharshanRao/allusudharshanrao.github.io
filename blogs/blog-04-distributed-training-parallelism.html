Distributed training in plain terms

Parts 1–3 focused on inference: phases on the GPU, how requests become facility load, and how to model serving power without smoothing away spikes. Training is a different beast—more synchronized, more repetitive, and often louder at the rack meter.

This post names the bulk-synchronous loop, the main parallelism strategies, and why that rhythm shows up as structured electrical load.

The bulk synchronous loop

Most frontier training jobs use bulk synchronous parallel (BSP) execution. Everyone advances in lockstep: compute together, synchronize together, then repeat. One training step is usually described as four phases.

PhaseWhat happensTypical power
ForwardActivations flow through the model; loss is computedHigh, compute bound
BackwardGradients flow back through layersHigh, compute bound
SynchronizationGradients combined across workers (often all reduce)Lower, communication bound
UpdateOptimizer applies gradients; weights changeModerate, memory heavy

Forward and backward keep tensor cores near busy. Synchronization shifts work toward the network: collectives, waits for peers, less arithmetic per joule. The cluster breathes between a high compute plateau and a communication dip, step after step, for hundreds of thousands of iterations.

Worked example: eight GPUs, data parallel

Imagine 8 GPUs in one data-parallel group, each with a different micro-batch. They run forward and backward locally, then execute one all-reduce so every replica holds the same averaged gradient, then apply the optimizer. Wall-clock for the step is roughly:

tstep ≈ tforward + tbackward + tallreduce + tupdate

If forward+backward take 400 ms and all-reduce takes 120 ms, communication is ~23% of the step—and during that 120 ms the fleet is synchronized in a communication-heavy, lower-power phase. Scale to 8,192 GPUs and the same pattern holds: the barrier still aligns everyone, which is why facility meters see rhythmic swings.

Why the rhythm matters for power

One GPU dipping during a collective is irrelevant to a substation. Ten thousand GPUs dipping together is not. Because BSP ties them to the same barrier, phase changes align. Facility load can move by tens of megawatts in seconds when the fleet leaves backward and enters all reduce, then snap back when compute resumes.

That is a different problem from total energy use. You can budget kilowatt hours and still be surprised by ramp rate, peak to mean ratio, and repetitive spectral content in the trace. Grid equipment and contracts care about those shapes.

Checkpointing adds a slower pulse on top of the per step rhythm: periodic saves that shift work toward storage and change the cluster profile for minutes. Same synchronized idea, lower frequency.

Four ways to split the work

No single strategy scales to trillion parameter class models alone. Real jobs combine dimensions. Think of them as answers to different bottlenecks.

Data parallelism

Each worker holds a full model copy. The dataset is sharded; each GPU sees different examples. After backward, gradients are averaged with all reduce so every replica stays identical. Synchronization happens once per step per data parallel group.

Tensor parallelism

Large layers are sliced across GPUs in the same node. Attention and MLP matrices are split; partial results are merged with collectives inside the layer. Bandwidth inside the node (NVLink on NVIDIA stacks) matters because communication happens every layer, not once per step.

Pipeline parallelism

The model is cut into stages on different devices. Microbatches flow forward through the pipeline; gradients flow back. Without careful scheduling, early and late stages sit idle waiting for the pipeline to fill, the pipeline bubble. Schedules that interleave forward and backward on different microbatches shrink the bubble but do not erase it. Power at stage boundaries reflects that uneven utilization.

Expert parallelism

For mixture-of-experts models, experts live on different GPUs. Tokens are routed to a subset of experts each step. That needs all-to-all style communication per MoE layer so tokens reach the right machines and results return. Load balancing losses keep a few experts from hoarding all traffic.

Hybrid configs at scale

Frontier runs multiply the dimensions. A compact mental model:

Data parallel (DP)     replicas across groups
Tensor parallel (TP)   split layers inside a node
Pipeline parallel (PP) stages across nodes
Expert parallel (EP)   experts for MoE layers

Total GPUs ≈ DP × TP × PP × (EP when MoE)

Each GPU may belong to several overlapping communication groups at once: all reduce for DP, in layer collectives for TP, point to point for PP, all to all for EP. Frameworks like Megatron style layouts exist precisely because managing those overlaps without leaving GPUs idle is hard.

Can you train without sync?

Asynchronous variants let workers use slightly stale gradients. They can help in some regimes but hurt convergence when batches are huge and consistency matters. Frontier quality training still defaults to synchronous steps, which means barriers and collectives are not optional decorations. They are the price of one shared model.

Engineering then shifts from “remove sync” to “live with the waveform”: overlap communication with compute where possible, shape transients at the rack, and model the facility trace honestly.
