Modeling inference power without hiding the spikes

Capacity planning for LLM serving often starts with a comfortable number: average utilization, average watts per GPU, multiply by fleet size. That number is useful for finance. It is dangerous for electrical design.

Part 1 named the GPU phases; Part 2 traced how requests become facility load and what to meter. Here we build synthetic power traces from traffic assumptions while keeping spikes and ramps in the model.

Why averages fail

Imagine a cluster that reports 60% average GPU utilization and 420 W average draw per chip. Multiply by server count and you get a headline facility load. That load is real in some accounting sense. It is not what decides whether a breaker trips during a viral spike.

Averages hide:

  • Short prefill bursts that push individual GPUs toward 700 W or more for seconds
  • Long decode stretches where many GPUs sit in a moderate, steady band
  • Correlated prefill when many requests land at once
  • Fast ramps when phase mix changes faster than delivery equipment likes

Design around the mean and you either overbuild forever or underbuild for peaks you never modeled. High-fidelity traces expose peak-to-mean ratio, ramp rate, and how often the fleet oscillates. Those are the quantities infrastructure people actually need.

Four stages: traffic to facility load

A practical trace model chains four transformations. Each stage has a clear input and output.

Stage 1: traffic to workload features

Start from assumptions you can defend: arrival rate, prompt length distribution, output length distribution, maybe a diurnal curve. Turn them into a discrete time series of workload features at each step.

Typical features include active request count, change in active requests (arrivals minus departures), batch occupancy, and estimates of how much of the batch is in prefill versus decode. You are not predicting power yet. You are describing demand in a form a temporal model can read.

Stage 2: features to power state labels

Each time step gets classified into one of a small set of power states. That is a sequence problem: the label at t depends on what happened at t − 1 and what is about to happen. A bidirectional GRU (BiGRU) is a common choice because it reads context forward and backward along the trace.

The states themselves should not be guessed from folklore alone. Fit a Gaussian mixture model (GMM) on measured power telemetry first, then attach names like prefill dominant or decode dominant by comparing cluster means to known execution behavior. Discovery and labeling are separate steps on purpose.

Stage 3: state trajectory to per server trace

Each state maps to a power distribution, not a single watt value. Prefill dominant might be high mean, moderate variance. Idle might be low mean with a floor from warm memory and background services.

Given a sequence of states, sample or draw from the matching distribution step by step while respecting transition statistics learned from data. The output is a synthetic but plausible watt trace for one server over time.

Stage 4: server traces to facility aggregation

Sum traces across racks with an explicit correlation model. Servers that receive traffic together will spike together; independence assumptions underestimate peaks. Apply PUE as a function of IT load when you can, not as one scalar multiplier for all conditions. The result is facility demand at the point of common coupling (PCC), where the grid meets the datacenter.

Discovering states with a GMM

Real serving rarely sits in exactly three neat boxes. Continuous batching creates mixed phases. Idle is not zero watts. A GMM treats the observed power histogram as a weighted sum of Gaussian components. Fitting reveals how many statistically distinct modes exist and their means and variances.

After fitting, hard labeling assigns human readable names. The highest mean, tightest cluster often maps to prefill dominant. The lowest mean with broad spread often maps to idle. Middle clusters become decode dominant or mixed depending on workload features at the same step.

Four inference power states

Once labeled, the four states line up with how operators already think about serving:

  • Prefill dominant. High power, short duration. Full sequence forward passes, KV cache written, tensor cores busy.
  • Decode dominant. Moderate power, long duration. One token per step, cache reads dominate, draw below TDP but stable.
  • Mixed. Intermediate power and higher variance when some batch slots prefill while others decode.
  • Idle. Low but nonzero. Memory held, runtime resident, waiting for the next arrival.

Why a BiGRU for classification

A server that just finished prefill is more likely to enter decode than to jump straight to deep idle. A spike back to prefill dominant power usually means new work arrived, not random noise. Those are temporal rules.

A model that classifies each step alone misses them. A BiGRU does not. Forward and backward passes over the feature sequence let each label use past and future context, which stabilizes state sequences and produces traces that look like measured data.

Features per step t (example):
  A_t        active requests
  dA_t       change in active requests
  occupancy  fraction of batch capacity used
  queue_len  requests waiting for prefill

BiGRU → state label s_t in {PREFILL, DECODE, MIXED, IDLE}

Map s_t → sample P_t from state specific distribution

Dense models vs mixture of experts

Dense models activate essentially all parameters every token. Power per state is relatively predictable for a given batch shape.

MoE models route each token through a small expert subset. Decode power varies with which experts fire. Mixed state behavior shifts because decode arithmetic intensity differs from dense decode even when total parameter count is huge.

A trace model fit only on dense telemetry will misread MoE serving unless you retrain or apply corrections tuned to that architecture.

Aggregation, PUE, and PCC

Three effects matter when you roll server traces up:

  • Arrival correlation. Bursts align prefill across machines. Variances add; peaks grow.
  • Heterogeneity. Mixed model sizes and batching policies partially desynchronize swings, but rarely cancel them completely.
  • PUE. Facility load exceeds IT load by cooling, distribution, and auxiliary draw. PUE often worsens at partial load. Use a curve when you have one.

The PCC is the electrical interface to the grid. Utilities, interconnect studies, and reactive power planning care about PCC demand, not average watts per GPU on a dashboard. Getting PCC right requires the full pipeline, not a fleet average.

What you do with the trace

Once built, the same trace supports breaker and UPS sizing, tariff conversations where volatility matters, comparing batching policies without running every experiment on metal, and baselines for anomaly detection.

The point is not machine learning for its own sake. It is to keep spikes and ramps in the model so planners cannot pretend they are not there.
