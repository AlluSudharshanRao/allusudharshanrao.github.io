All-reduce and why training waits on the network

The last post described how thousands of GPUs march through forward, backward, sync, and update in lockstep. The sync step is not a detail. It is often where the cluster spends its wall-clock time and where power dips. That step is built from collective communication, and the workhorse collective for data-parallel training is all-reduce.

The gradient sync problem

In data parallel training, every GPU holds a full copy of the model. The dataset is split: GPU 0 sees batch A, GPU 1 sees batch B, and so on. Each device runs forward and backward on its own shard. The gradients they compute are correct for their shard, but they are not the gradients of the full dataset.

To take one honest optimizer step, the cluster must agree on a single gradient vector (or an average of local gradients that matches that vector). Every worker must apply the same update. Otherwise replicas drift apart and you are no longer training one model.

That agreement is the gradient synchronization problem. You have N tensors of the same shape, one per GPU, and you need the elementwise sum (or mean) visible on all N devices before anyone touches weights. At billion parameter scale, that tensor is enormous and must cross NVLink within a node and InfiniBand across nodes.

What all reduce does

All reduce is a collective operation. Each of N participants contributes a buffer. The group applies a reduction (usually sum) and returns the combined result to every participant. No single GPU is the “master” that alone holds the answer; everyone ends with the same final array.

For training, the buffers are gradients (or gradient buckets). After all reduce, each GPU has the global gradient and can run the optimizer identically. Frameworks hide this behind calls like distributed data parallel, but underneath it is still reduce, scatter, gather, or all reduce patterns scheduled by libraries such as NCCL.

Ring, tree, and hierarchical variants

Implementations differ in how they move bytes and how many steps they take. The choice matters for latency, link utilization, and how long GPUs sit in a communication heavy phase.

Ring all reduce

Workers are arranged in a logical ring. The algorithm runs in two phases. Reduce scatter walks chunks around the ring so each GPU ends up owning one fully reduced slice of the tensor. All gather then circulates those slices until every GPU has the full reduced tensor.

Ring all-reduce is bandwidth efficient: each link carries roughly twice the tensor size divided by N worth of traffic, and utilization improves as N grows. It is the default mental model for large data-parallel jobs on homogeneous fabrics.

Tree all-reduce

Tree reduction sums gradients up a binary tree, then broadcasts the result down. Step count scales like log N instead of linear in ring steps, which helps when messages are small and latency dominates. Large gradient tensors on modern LLMs are usually bandwidth bound, so pure tree is less common alone, but it appears inside hybrid schemes and for small tensors.

Hierarchical all reduce

Real clusters are not flat. Inside a server, NVLink offers very high GPU to GPU bandwidth. Between servers, NIC links are slower. Hierarchical all reduce respects that: reduce within the node on fast links, reduce across nodes on the fabric, then gather within nodes again. Less bits cross the expensive links, which shortens the collective and shrinks how long the fleet waits with tensor cores relatively idle.

Why training still waits

Even an optimal algorithm faces hard limits. Gradient size grows with model size. A single full model all reduce can move terabytes per step if you are not sharding cleverly. All reduce is also a barrier: the collective cannot start until the slowest GPU finishes the backward pass for the tensors in that bucket, and the optimizer cannot run until the collective finishes.

Tensor parallel and pipeline parallel training add more collectives (all gather, reduce scatter, point to point activations). ZeRO style sharding changes what is replicated and what is communicated, but it does not remove the need to move data. It redistributes memory pressure into different communication patterns.

So when people say training is compute bound or communication bound, they mean iteration time is limited by matmul throughput or by how fast the fabric can finish these collectives. At frontier scale, both bite, and the communication slice is what forces synchronized, mostly idle GPUs.

Overlap with backward

Waiting until the entire backward pass ends before starting any communication would waste time. Production stacks bucket gradients: group layers into chunks of roughly tens of megabytes. As soon as a bucket’s gradients are ready, launch all-reduce for that bucket while deeper layers still compute.

PyTorch DDP, Megatron style schedules, and DeepSpeed all exploit this pipeline inside the backward pass. NCCL runs collectives on separate CUDA streams so copies and reductions can overlap with matmuls on other streams.

Overlap improves throughput and can smooth the power trace a little, but it does not erase phases. The first buckets still wait for early layers. The last bucket must finish before the optimizer runs. Stragglers on the network still stall everyone. You have reduced wall clock; you have not removed the collective as a shared rhythm.

Power during communication vs compute

During forward and backward, tensor cores and matrix units run hot. Power approaches thermal design power. During all reduce, arithmetic intensity collapses. Cores are not doing dense GEMMs. Instead DMA engines, NVLink ports, NICs, and memory controllers move data. Power usually drops, sometimes to a clear trough between compute peaks.

Communication is not free electrically. Links draw power. Memory copies cost energy. A GPU in a collective is busy, just not in the way that maxes out FP8 tensor throughput. Facility meters still see a dip relative to compute peaks because the silicon is doing less math per watt.

Overlap mixes the two: some GPUs compute while others communicate, or one device does both on different units. The aggregate rack power becomes a blend, but at large scale the barrier edges remain. When the last all reduce completes and the optimizer fires, or when the next forward pass starts, thousands of devices can shift state together again.

That is the link to power infrastructure. All reduce is why the “sync” phase in the training loop exists electrically, not only in software. Optimizing the network makes training faster; it does not remove the synchronized dip unless you change the training model itself.
