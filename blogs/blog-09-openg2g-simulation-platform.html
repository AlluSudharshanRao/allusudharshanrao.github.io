Inside OpenG2G: simulating datacenter and grid together

Part 9 · OpenG2G co-simulates a datacenter backend, a grid backend, and pluggable controllers on a multi-rate loop [1].

Why one simulator is not enough

Grid papers rarely run vLLM. ML papers rarely run OpenDSS. OpenG2G stitches both: measured inference behavior drives datacenter power, while a distribution feeder simulator returns voltages and violations. Controllers sit in the middle with a small Python API—swap a policy, a model mix, or an IEEE test feeder without rewriting the loop.

Datacenter backend: measurements, not guesses

By default the datacenter replays ML.ENERGY Benchmark traces: power, throughput, and latency for production-style inference stacks [7,8]. You configure model (Llama, Qwen, GPT-OSS, etc.), GPU type, latency target, and replica schedule. Controllers change batch size or replica count; the backend returns realistic tradeoffs. Training jobs can be overlaid with traces from large-model training runs [49 in 1].

Grid backend: distribution feeders

The stock grid wraps OpenDSS on IEEE 13-, 34-, and 123-bus test feeders [12,21,24]. Primary objective: keep voltages in band. Reducing datacenter demand helps undervoltage; increasing demand can help overvoltage when the feeder has excess generation.

Multi-rate simulation loop

Each tick may advance datacenter, grid, and controller at different fractional rates (e.g. 0.1 s datacenter steps). Grid power flow can be expensive; inference may need fine-grained power timelines. Centralized logging and seeding keep scenarios reproducible.

Read datacenter + grid state
↓
Controller computes commands
↓
Apply batch / replica / tap changes
↓
Log power, tok/s, voltages, violations

Feasible power range: the flexibility budget

Before picking a controller, ask how far the datacenter can move. OpenG2G uses feasible power range (MW): max minus min datacenter power over inference configs that still meet the per-token latency target [1, §5]. With batch size as the main knob, the endpoints are the smallest and largest batches that respect latency.

Wider span → more room to help the grid. Narrow span → coordination fights the hardware floor or the latency ceiling.

Experiments anchor peak power (e.g. 3 MW at max batch) so comparisons isolate model and deployment choices, not “how many GPUs you bought” [1, §5].
