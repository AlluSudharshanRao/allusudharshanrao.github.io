How LLM inference actually runs

People talk about an LLM server as if it is one steady job. It is not. A single request moves through distinct stages, and each stage stresses the GPU differently. If you care about latency, batching, or power, you need to know which stage you are in.

Prefill: chew through the prompt

When a prompt arrives, the model processes every input token at once. Embeddings, attention over the full context, layer after layer. Along the way it fills the key-value (KV) cache, the per-request store that decode will read from later.

Prefill is short and heavy. Matrix work is large, tensor cores stay busy, and power can sit near the chip’s rated limit. Long prompts hurt more than linearly because attention cost grows with sequence length squared, not just length.

Decode: one token at a time

After prefill, generation is autoregressive. Each step adds one token, reads the cache, runs a thin forward pass, samples or picks the next token, and repeats. Arithmetic intensity drops: you are not doing giant matmuls on the whole sequence anymore. You are mostly feeding weights and cache lines from HBM.

Decode often draws less peak power than prefill, but it can run for a long time on chatty or agentic outputs. A fifty-token reply is brief. A multi-thousand-token trace keeps the GPU in decode for minutes.

Idle is not off

Between requests the GPU is quiet, not dead. Memory stays allocated, runtimes stay warm, health checks still run. Power falls, but there is a floor you still pay for on always-on serving fleets, and bursty traffic makes the trace jump between idle and active all day.

Worked example

Suppose a user sends a 200-token prompt and the model returns 400 tokens. Prefill might take on the order of tens to a few hundred milliseconds on a modern GPU (model and batching dependent). Decode runs 400 forward passes—one per output token—so it often dominates wall-clock time even though each decode step is cheaper than prefill.

Latency-wise, time-to-first-token (TTFT) is almost entirely prefill. Time-per-output-token reflects decode. Tuning batch size helps throughput; it does not turn decode into prefill. Power-wise, you may see a sharp prefill spike followed by a long plateau near moderate draw—a shape the rest of this series builds on.

Continuous batching blurs the lines

Naive serving finishes request A, then starts B. Production systems use continuous batching: new prompts can join while others are still decoding. The scheduler slips prefill into the same iteration as ongoing decode work.

Throughput goes up. Utilization improves. The clean picture of “prefill, then decode, then idle” stops matching reality. At any instant one GPU might be decoding for two chats and prefilling a third. Power sits between the pure phases and shifts as the mix changes.

That mix also tightens memory. Every in-flight request owns KV cache space that grows with each generated token. Frameworks like vLLM use PagedAttention so HBM does not fragment as requests come and go. Without that, concurrency caps bite fast.

Dense models vs mixture of experts

Dense models touch essentially all parameters every token. MoE models route each token through a small subset of experts. Total parameter count can be huge while per token compute is lower, but routing and load balance add their own mess. Prefill vs decode still exists; the numbers just differ, and power models trained only on dense stacks will miss MoE behavior.

Why this matters outside the GPU

Time to first token is mostly prefill. Time per output token is mostly decode. You cannot fix one by tuning the other.

Power planning sees the same split. A fleet of long prompt traffic holds chips high longer. Light traffic oscillates between spikes and idle. Capacity, routing, and scale out rules all depend on which phase dominates your workload.
